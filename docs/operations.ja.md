## バックアップとリストア { #backup-and-restore }

データベースは WAL モードで動作する単一の SQLite ファイル (`CPERSONA_DB_PATH`)
です。**稼働中の WAL データベースを単純な `cp` でコピーすると、チェックポイントをまたいで破損したコピーができえます**。 スクリプト化しないでください。

推奨する順に挙げます。

1. **オンライン物理バックアップ** (第一の選択肢。サーバーの稼働中でも安全)。

   ```bash
   sqlite3 "$CPERSONA_DB_PATH" ".backup 'cpersona-backup.db'"
   # または
   sqlite3 "$CPERSONA_DB_PATH" "VACUUM INTO 'cpersona-backup.db'"
   ```

   どちらも並行書き込み下で一貫したスナップショットを作ります。

2. **オフラインコピー**: サーバーを停止し、`.db` を **`-wal` と `-shm` の
   ファイルごと**コピーします。

3. **論理バックアップ** (低頻度の補完として推奨): `export_memories` は
   スキーマバージョンに依存しない JSONL を書き出し、`import_memories` は
   冪等です (すでにある記憶とエピソードはスキップ)。プロファイルはインポートがスキップせずに置き換える唯一のレコードです。ファイルの内容が保存済みの
   プロファイルを置き換えますが、保存済みのほうが新しい場合は保存済みのものを
   残し、その行を `errors` で報告します。したがって古いエクスポートでの訓練が
   プロファイルを過去に戻すことはありません。月次程度が妥当な頻度です。
   ファイルは記録に加えて宣言された連想 (entity・別名・言及・関係) も運び、
   リストアはそれを復元した記録へ向け直します。以前のバージョンが書き出したファイルは
   連想を含まず、これまでどおり取り込めます。2.4.37 以前が書き出したファイルは
   project と channel の軸も含まないため、その行はすべてのプロジェクトから
   読まれるグローバルプールに復元され、インポートはその件数を `errors` で
   報告します。インポートは
   `CPERSONA_MAX_IMPORT_BYTES` (既定は 100 MiB) より大きいファイルを拒否し、
   エクスポートにはこの上限がありません。バックアップファイルごとにサイズを
   この値と比べ、リストアで必要になる前に引き上げてください
   ([設定](configuration.md#export-and-import))。

**`.db` はインスタンスの全体ではありません。** データベースの外に状態があり、
上のどのバックアップ手段もそれらに触れません。

- `<CPERSONA_DB_PATH>.calibration.json`: エージェント別のベクトル閾値・
  ゲート状態・スコアリングのバージョン、エージェント別の `set_recall_precision`
  の beta。

    このファイルなしで復元しても、測定値は自動で復旧します。既定の
    `CPERSONA_CALIBRATE_ON_MODEL_CHANGE=true` では、sidecar が無い起動は
    フォールバックではなく再較正を行い、それが起きなかった場合は `deep_check`
    が `never_calibrated` を報告します。

    **beta は復旧しません**。beta は測定値ではなくポリシーの入力であり、
    運用者が指定した好みを導き直す仕組みはありません。precision を調整していた
    運用者は、知らされないままその調整を失い、再較正は全ゲートを既定の
    beta で測ります。sidecar をデータベースと並べてコピーするか、復元後に
    `set_recall_precision` を再適用してください。
- `~/.cpersona/operating-context.toml` (または
  `CPERSONA_OPERATING_CONTEXT_PATH`): 全クライアントに配られる運用者の指示。
- `CPERSONA_ACL_FILE` を設定しているなら、その ACL ファイル。このファイルなしで復元
  すると、誰が接続できるかが変わります。
- **別名台帳 (alias ledger)**: どれかの ACL 行が `per_subject` を設定している
  場合。データベースと並ぶ `alias_ledger.json`、または
  `CPERSONA_ALIAS_LEDGER_FILE` が指すファイルです。サーバーは subject が初めて
  サインインした時にこれを書き込み、どの `u-` エージェントが誰のものかを記録
  しているのはこのファイルだけです。このファイルなしでデータベースを復元すると、
  サーバーはそれらのエージェントを名指しして起動を拒否します。台帳をその
  パスに戻してから、サーバーを再び起動してください。代わりにエージェントを
  改名したり `per_subject` を外したりしないでください。どちらを行っても、
  サインイン済みの subject はすべて新しい別名を受け取り、保存した記憶に
  届かなくなります。
- **外部ベクトル索引**: `CPERSONA_VECTOR_SEARCH_MODE=remote` かつ
  `CPERSONA_STORE_BLOB=false` の構成の場合。この構成では埋め込みがリモート索引
  にしか存在しないので、データベースと上記のファイルをすべて戻しても、ベクトルの
  アームが空の状態で復元されます。`check_health` は `no_local_vector_fallback` と
  して報告します。索引も同じ頻度でバックアップするか、`STORE_BLOB=true` のまま
  にして `.db` を自己完結に保ってください。
- **`<CPERSONA_DB_PATH>.memories.vecindex` と `.episodes.vecindex` (連続ベクトル
  索引) は含めません**。データベースから導出される派生物で、リストアするもの
  ではなく作り直すものです。バックアップに含めても容量の無駄で、古い索引が
  戻ってきても次の build で正されます。
  [連続ベクトル索引](#the-contiguous-vector-index) を参照してください。

稼働中のデータベースは**クラウド同期フォルダの外**に置いてください
(Dropbox、Drive など)。同期クライアントは SQLite の WAL ファイルと相性が
悪いためです。同期するのは*バックアップ*のほうにしてください。

## 埋め込みサーバー停止の検知 { #detecting-a-dead-embedding-server }

ベクトル検索は最も強い検索層ですが、誰も見張っていなければ、ネットワーク境界で
**知らせなしに**劣化します。検知の手段は 3 つあり、呼び出し側のエージェントには
1 番目を見るよう指示してください。

1. **recall 応答の `advisory`** (v2.4.33 以降、主な検知の手段)。状態機械が実際の
   埋め込み失敗を観測し、劣化した recall には
   `advisory = {degraded, severity, reason, evidence, runbook, advisory_scope}`
   が付きます。「ベクトル層が落ちている。FTS + keyword のみで応答中」という
   意味です。

    このフィールドをユーザーに提示し、その `runbook` に従うようエージェントに
    指示してください (通常は「埋め込みサーバーを起動または向け直してから再度
    recall する」)。runbook が短縮されている場合は「もう伝えた」という意味です。
    その「誰に」を述べるのが `advisory_scope` で、プロセスが自分専用なら
    `session`、HTTP トランスポートでは状態がサーバー全体のものなので `process`
    になります。共有サーバーでは、fault は自分のセッションが見たと仮定せず
    完全版 runbook を繰り返します (bug-251)。

    `CPERSONA_DEGRADED_ADVISORY=false` は advisory を出さないようにします。埋め込み
    バックエンド無しでの運用を運用者が受け入れたことを記録する用途で設定して
    ください。これはサポートされる fallback であって、推奨構成ではありません。
    設計: [DEGRADED_ADVISORY_DESIGN](DEGRADED_ADVISORY_DESIGN.md)。
2. **store 応答の `embedded`**。すべての書き込みが、自分の埋め込みが永続化された
   かどうかを報告します。サーバー停止中に行われた書き込みは `embedded: false`
   で返り、それらの行は修復可能です (次項)。
3. **`check_health(agent_id, fix=true)`** は、埋め込みが NULL のまま保存された
   行を検出し、サーバー復帰後に再埋め込みします。エンドポイントに到達できない
   場合、次元チェックは今も*失敗ではなくスキップ*されますが、エンドポイント
   自体は見張られるようになりました。構成済みのバックエンドが応答しない時、
   `embedding_backend` が、失敗した呼び出し自身の証跡を添えて `warn` を報告
   します。その実行自身の probe がバックエンドに届いてベクトルが返った場合、
   その応答は以前に latch された fault より優先されます。再起動したバックエンドは
   接続済みとして読まれ、その NULL 行は同じ実行で再埋め込みされます。
4. **`not_probed` はそのままの意味で読んでください**。 `check_health(fix=false)`
   は生存を判定しません。バックエンドへの接続は起こりえます (次元チェックは
   probe 用のテキストを埋め込み、モデルチェックはバックエンドの identity を問い、
   ノード走査はトークン数を問います) が、どの呼び出しも生存の証拠としては
   読みません。何も出ないことから健全だと推測させる代わりに、`embedding_backend` が
   `not_probed` を返し、判定していないことを明示します。

    `fix=true` の実行でも、probe が埋め込みクライアントの 5 分間キャッシュから
    応答された場合には、同じものを返します。次元はエンドポイントに要求が届かない
    まま返るので、そこからは何も分かりません。2 つのどちらであったかは、finding の
    `reason` に書かれます。recall が既に latch した fault は、そこでも報告されます。

    バックエンド未構成の場合、このチェックは意図して報告を控えます。それはサポート
    された構成であり、提起するのは `advisory` の面だからです。

## recall のチューニング { #tuning-recall }

使うべき順に、つまみを挙げます。

1. **`set_recall_precision(agent_id, precision)`**: 主なポリシーのつまみで、
   既定の融合モードでは事実上唯一のものです。融合品質ゲートの動作点 β を動かし
   ます。`strict=2.0` (混入が減り、取りこぼしが増える)、`balanced=1.0` (既定)、
   `lenient=0.5` (取りこぼしが減り、混入が増える)。すぐに反映され、再起動は不要です。
2. **`calibrate_threshold(agent_id)`**: コーパスからゲート位置を導出し直します
   (ラベル不要)。`agent_id` **付き**で (かつ融合ゲート有効で) 呼ぶと、ベクトル
   閾値と融合ゲートの**両方**を較正します。付けずに呼ぶと、ベクトル閾値のみを
   較正します。表示される値はベクトル側の閾値ですが、融合モードで実際に結果を
   切っているのは融合ゲートです。コーパスが大きく変わった後、一括再構築の後、
   埋め込みモデルを変えた後に再実行してください。
3. **`CPERSONA_AUTOCUT_MIN_RESULTS`**: autocut は類似度スケールのシグナルに
   対して発火します。confidence スコアリング下、あるいは生の cosine だけで
   構成された均質なリスト (`cascade` が作るのがそれで、confidence の on/off は
   問いません) に対してです。`rsf` / `rrf` では意図して働かせていないので
   ([契約 §6](behavior-contracts.md#6-autocut-fires-only-on-similarity-scale-signals))、
   既定構成ではこのつまみは何もしません。それを決めているのは融合モードであって、
   confidence フラグではありません。
4. **`CPERSONA_FUSED_GATE_ENABLED=false`**: 最後の手段です。ゲートが無いとフィルタ
   はプール規模のヒューリスティック (`_adaptive_min_score`) にフォールバック
   しますが、それでも弱い一致は弾かれます。開けっ放しになるのではなく、粗い
   ゲートになるということです。失うのは*このコーパスに対して*測定された動作点
   です。

**precision の選び方**。トレードオフは用途ごとに非対称です。索引的なコーパス
(無関係な行を捨てられる AI に recall の結果を渡す) では**取りこぼしの方が
混入より悪い**ので、数日 `lenient` で運用し、混入が実コストになった場合にのみ
`balanced` に戻してください。混入に敏感な文脈 (狭い窓に recall を注入する)
では `balanced` / `strict` を選んでください。

### recall に頼らないという選択 { #when-not-to-rely-on-recall }

確率的検索は負けることがあります。*文脈に無いこと自体が害になる*事実 (現在の
最優先の決定、常時有効な安全ルール) は、記憶ではなく**決定的に注入される場所**
(`CLAUDE.md`、システムプロンプト、エージェントが常に読む索引ファイル) に置いて
ください。

有用な切り分けは、*問われずに発火すべきものは決定的な注入へ、問われたときに
見つかればよいものは記憶へ*です。ここから、次の 2 つが導かれます。

- **決定の更新は追記でなく上書きで行う**。決定が変わったら古い行を
  `update_memory` してください (自動で再埋め込みされます)。古くなった決定が
  recall に勝つのを止める最も確実な方法は、それが検索の対象に残っていないことです。
- `lock_memory` は消失からは守りますが、順位で負けることからは守りません
  ([契約 §9](behavior-contracts.md#9-lock_memory-protects-it-does-not-boost))。

### Claude Code のフックから recall を促す { #prompting-recall-from-claude-code-hooks }

エージェントは答える前に必ず記憶を引くとは限りません。常時読み込まれるファイルに書いた指示は
一度読まれたきりで、ほかのすべての内容と注意を奪い合います。フックはその時点で発火します。
エージェント用のプラグイン ([はじめに](getting-started.md#let-the-agent-do-it-claude-code)) は、
Claude Code と Codex のどちらにも 3 つのフックを入れます。セッションの開始時、発言のたび、
会話が圧縮された後です。発言のたびのフックはその依頼について `reconstruct` を呼ぶこと (発言を
問いの候補として添えます) と、「その記録はありません」はスコアでなく完全一致の検索で確かめることを、
文脈に書き足します
([契約 §12](behavior-contracts.md#12-scores-order-one-response-they-do-not-say-whether-an-answer-exists))。
手で登録したい場合のソースは
[`plugin/scripts/cpersona_hooks.py`](https://github.com/Cloto-dev/CPersona/blob/master/plugin/scripts/cpersona_hooks.py)
です (標準ライブラリだけで書いています)。

Windows では、次の 2 つの誤りが気づかないうちに失敗を招きます。ある実運用の利用者は、手で登録した
フックで両方に当たり、5 日間 recall が一度も働きませんでした。プラグインのフックは両方に対処しています。

- **UTF-8 の読み書きは自分で行う**。Windows では Python の標準入出力がコンソールのコードページ
  (日本語版 Windows では cp932) を使い、Claude Code は UTF-8 で送受信します。`sys.stdin` を文字列
  として読むフックは日本語の発言で失敗し、何も足しません。プラグインのフックはバイトで読み書きし、
  UTF-8 の変換を自分で行います。
- **スクリプトは絶対パスで指定する**。相対パスは、セッションの作業ディレクトリがサブフォルダの時に
  見つからなくなります。プラグインは `${CLAUDE_PLUGIN_ROOT}` でスクリプトを指定します。手で登録する
  フックでは、プロジェクトのルートに展開される `$CLAUDE_PROJECT_DIR` を使えます。

## 日本語 / CJK コーパス { #japanese-and-cjk-corpora }

- **`CPERSONA_RECALL_MODE=rsf`** を設定してください。FTS5 は CJK のトークン化が
  苦手ですが、rsf はマージの際に keyword チャネルのスコアの大きさを保持し、
  それが弱点を補う手がかりになります。これ以外に CJK 固有の設定はありません。
- `jina-v5-nano` (本プロジェクトが動かしているモデルで、参照実装の埋め込み
  サーバーが既定でダウンロードするモデル) には、日本語で次の既知の特性があります (長期の
  本番運用で確認済み)。クエリと記憶の間に**固有名詞や識別子のアンカーが 1 つ
  以上重なるときは強い**一方、**共有語彙のない純粋な概念一致には弱い**です。
  具体的なアンカー語を含めてクエリを書くこと (「キーワードアンカリング」) は、
  現行モデルに合った正しい使い方であって、後ろめたく思うべき回避策ではありま
  せん。
- モデルスロットは差し替え可能です (`CEmbedding` プロバイダ)。埋め込みモデルを
  入れ替える場合は、コーパス全体を再埋め込みしてから `calibrate_threshold` を
  実行してください。サーバーは*次元*が変わったときは自動で再較正しますが、
  同一次元のモデル入れ替えでは手動の再較正が必要です。

## コーパス索引と同期のパターン { #corpus-indexing-and-sync-patterns }

CPersona の設計の中心は、まず会話から積み上がる記憶です。**元となる Markdown
ファイルの検索索引**として使うこともできますが、正しいパターンは次の 2 つの
事実で決まります。CPersona が**受動的なサーバー**であること (ファイル監視は
なく、取り込みは常に呼び出し側が行う) と、重複排除が **upsert ではなく
skip** であること ([契約 §5](behavior-contracts.md#5-dedup-semantics-skip-not-upsert))
です。

**パターン A: 索引を使い捨ての派生物として作り直す (まずはこちらを推奨)**。

1. 索引に**専用の `agent_id`** を与えます (例: `md-index`)。索引チャンクを会話
   エージェントの記憶に混ぜないでください。分けておけば、エピソード境界の機構も
   絡んできません。
2. 元ドキュメントが変わったら `delete_agent_data(agent_id="md-index")` を実行し、
   全チャンクを再 `store` します。
3. **再構築のたびに `calibrate_threshold` を再実行してください**。
   `set_recall_precision` を使っているなら、それも再適用します。
   `delete_agent_data` は、その agent の行と一緒に較正状態も破棄するためです。
   再構築が夜間バッチなら、再較正もバッチの一部にします。
4. コスト: 数千チャンクの再埋め込みは CPU で数分〜数十分です (環境依存)。
   得られるのは、差分ロジックが不要になることと、再構築が終わった時点で索引が
   ソースと一致することです。

    再構築の**最中は一致しません**。`delete_agent_data` は再 `store` が始まる
    前にコミットするので、その間に発行された recall は、部分的な索引か、
    何も無い索引を見ます。誰も問い合わせていない時間に再構築するか、第 2 の
    `agent_id` の下で構築して、完成後に読み手を切り替えてください。

**パターン B: 外部の内容ハッシュの一覧による差分更新**。

1. 各チャンクを、安定した `msg_id` (例: `path#heading`) と、`source.id` に入れた
   元ドキュメントとともに `store` します。こうすると recall の `source_id` 引数
   が、ドキュメント単位のフィルタとしても使えます。英字か数字で終わる値
   (`docs/a.md`) はその 1 ドキュメントにだけ完全一致し、区切り文字で終わる値
   (`docs/`) はその下のすべてのドキュメントに前方一致します。
2. 呼び出し側で `キー → 内容ハッシュ` の一覧を保持し、ハッシュが変わった
   チャンクだけを処理します。
3. **変更されたチャンクは必ず `update_memory` (または `delete_memory` +
   `store`) を通してください**。同じ `msg_id` で変更後の内容を再保存しても、
   何も知らされずにスキップされます。変更のないチャンクは何も考えずに再投入して
   構いません。完全一致の重複排除がそれを無害だと保証します。

再構築の時間が実際に負担になるほどコーパスが大きくなるまでは、A を選んでください。
壊れる一覧がなく、ずれていく状態もありません。

## スケール { #scale }

成長にアーカイブや間引きの定期処理は不要です。ベクトル層は新しい順のウィンドウ
(`CPERSONA_MAX_MEMORIES`、既定 10,000) を走査します。FTS と keyword のチャネルは
全履歴に届き、古い行は削除されるのではなく、ウィンドウと減衰によって下位に回ります。

ベクトルのアームをウィンドウより先の行に届かせるには、`CPERSONA_VECTOR_REACH` を
ウィンドウより大きく設定するか、窓の外の席 (`CPERSONA_FAR_SEATS_ENABLED`) を
有効にしてください。ウィンドウ自体を広げると、それが与えている新しさの事前分布も
失われます。実測では、新しい答えで NDCG@10 を 20 ポイント失い、古い答えで 5 ポイント
得ました ([契約 §4](behavior-contracts.md#4-the-vector-scan-window-cpersona_max_memories))。

## 連続ベクトル索引 { #the-contiguous-vector-index }

ローカルのベクトル走査は窓の中の埋め込みを SQLite から 1 行ずつ読み出します。
走査の時間の大半は計算ではなくこの読み出しです。連続ベクトル索引は、同じ
埋め込みを計算に都合のよい並びで持つ、データベースの横に置くファイルで、走査はそれを一度に
読みます。行も、スコアも、順序も同じで、変わるのはレイテンシだけです。基準の
マシンでは 100,000 行で、ベクトル側が 604 ms から 77 ms になりました。

索引はテーブルごとに 1 つです。memories と episodes は別々に走査されるので、
ファイルも別で、build も検査もそれぞれ行います。索引の無い episodes テーブルは、
その 5 倍の行数を持つ索引済み memories テーブルよりクエリあたりの費用が高いので、
片方を build する運用なら両方 build してください。

**派生物です**。元のデータはデータベースだけで、索引はそこから作った写しです。キャッシュと
同じように扱い、バックアップせず、修復せず、いつ消しても安全です。何かおかしく
見えたら、ファイルを消して build し直してください。

**変更ログを通して読みます**。ファイルが持つ行は build の後に変わることがあります。
`update_memory` が本文とベクトルを置き換える、埋め込み欠落の修復がベクトルを埋める、
再タグ付けで移る、修復が時刻を書き換える、削除される、といった場合です。トリガーがそうした行の id を
すべて記録し、クエリはその行をファイルでなくデータベースから読むので、答えは走査と
同じです。ログが動くのは索引ファイルがある間だけです。`build` がログを有効にし、ファイルが
1 つも残っていなければサーバーが起動時に止めます。ログができる前に書かれた索引ファイルは
使えないものとして拒否されるので、アップグレード後に build し直してください。

`delete_agent_data` は持っていた行と一緒にこのファイルも消しますが、それは呼び出し元の
権限がすべての agent に及ぶ時だけです (ACL が無ければ常に)。ファイルはすべての agent の
行を持つので、1 つの agent への権限はそこまで届きません。1 つの agent への権限での削除の後、
ファイルは次の build まで残りますが、その間も削除した行がそこから返ることはありません。
想起は候補をすべてデータベースから読み直すからです。削除がファイルを消した時にサーバーが
実行中だった build は、削除した行を戻さず、出力を捨てます。`build` コマンドは別のプロセスで
動き、削除との順序は取られないので、実行中に削除があったらもう一度実行してください。

**build は運用者の操作です**。稼働中のサーバーは索引を作りも更新もしません。
入口は cron や systemd timer から呼ぶためのコマンドです。

```bash
python -m cpersona.vector_index --db "$CPERSONA_DB_PATH" build
python -m cpersona.vector_index --db "$CPERSONA_DB_PATH" --table episodes build
python -m cpersona.vector_index --db "$CPERSONA_DB_PATH" status
python -m cpersona.vector_index --db "$CPERSONA_DB_PATH" --table episodes status
```

`--table` でファイルを選びます (既定は `memories`)。

`build` は行を書き換えずに読み、索引をアトミックに置き換えます。書き込むのは
変更ログのスイッチだけで、読む前にログを有効にし、後で存在するすべての索引ファイルが
既に持つログ行を捨てます。サーバーは次のクエリで新しいファイルを拾うので、再起動は不要です。
build できれば exit 0、見送ったら exit 1 で理由を表示します。理由は、埋め込み
済みの行が無いか、2 種類の埋め込み幅が同時に存在するか (モデル変更の途中の
一時的な状態。再埋め込みが終わってから build し直します)、まだどのサーバーも
移行していないデータベースか (サーバーを 1 回起動します) のいずれかです。

`status` は、索引の有無と使用可否、保持行数、build 以降に書かれた行数と変わった行数を報告
します。加えて、毎クエリが索引でなくデータベースから読む行数 (`rows_read_exactly`)
も報告します。この数には、build 以降に書かれた行・変わった行と、build が索引に入れられずに
名前を挙げた行が入ります。後者は、`created_at` が標準の形でない行 (`excluded`) と、
まだ埋め込みの無い行 (`unembedded`) です。名前を挙げられた行は、埋め込みを得た
時点から読む費用がかかります。欠けた埋め込みを埋めるのは `check_health` の
`fix=true` がすることなので、その修復の後は `rows_since_build` が 0 のままでも
`rows_read_exactly` が増えることがあります。索引が無ければ exit 1、ファイルは
あるが使えなければ exit 2 です。変更ログがファイルを保証できなくなった場合も
使えない側に入ります。
どちらも `--json` を付けると機械可読な 1 行になります。

**memories では、`build` は粗探索の索引も書きます**。 1 つ目の隣に置く 2 つ目の派生
ファイル (`<データベース>.memories.coarseindex`) です。同じ行を、それぞれ 1 次元 1 ビットに
縮めて持ち、[1 ビット粗探索](BINARY_COARSE_SEARCH_DESIGN.md)で述べる到達だけが読みます。
読むのは、on にした時の窓の外の席と、時間の手がかりが期間のうち走査窓より後ろを探す時です。
後者は 2.6.4 から、ファイルがあれば既定で使います。扱いは連続配置の索引と同じで、バックアップせず、修復せず、消しても安全で、
削除 (purge) も同じ規則でこれを消します。両方のファイルを作る場合、`build` が
exit 0 を返すのは両方を作れた時だけです。`status` は粗探索の索引を `coarse` の下で報告しますが、
自分の exit code は変えません。設定が求めない限り、粗探索の索引を読むものは無いからです。

**設定が読む時は、健全性チェックが報告します**。 `CPERSONA_FAR_SEATS_ENABLED=true` か
`CPERSONA_CUE_COARSE_ENABLED=true` で、あるエージェントが走査窓の外に記録を持つ時、粗探索の
索引を使えない想起は、その記録すべての保存ベクトルをデータベースから読みます。答えは同じで、
費用が窓ではなくストアの大きさに比例して増えます。`check_health` は `coarse_index_absent`
(窓の外の記録数と 1 回の想起が読むバイト数つき)・`coarse_index_unusable`・
`coarse_index_dimension_drift`・`coarse_index_log_refused` を警告として、
`coarse_index_tail_grown` を観察として出し、両方の設定が off の間やストアが窓に収まる間は
何も言いません。

`CPERSONA_CUE_COARSE_ENABLED` が未設定 (既定) の時、時間の手がかりはファイルにしか尋ねません。
使えるファイルが無ければ、期間のうち窓より後ろは探さず、想起は `time_cue.remainder` でそう
伝えます。窓の外の席が off の間は、ファイルが無くても費用を払う想起が無いので、同じ 4 つの
状態は警告でなく観察 (info) として報告します。ベクトルをローカルで探す想起で、範囲が窓の外に
保存済みベクトルを持つ記録を 1,000 件以上持ち、ファイルが無い時は、エージェントが利用者に
伝えるための `suggestion` もセッションごとに 1 回付きます。ファイルの作成が自動で行われることはありません。

`check_health(checks=["coarse_index"], fix=true)` は、窓の外に記録が 1 件でもあればファイルを作り直します。
ファイルは全エージェントの記録を持つので、この修復は全エージェントへの書き込み権限を求めます。
所見は他のチェックと同じく `get_session_findings` に届くので、監視側は遅さとして誰かが
気づく前に費用を知ることができます。所見を受けて修復するかは監視側が決めることで、
サーバは決めません。

**build と build の間に起きること**。索引は build 時点の最大行 id を覚えて
います。それ以降に書かれた行は索引に無く、失われもしません。毎クエリがそれらを
データベースから厳密に読み (走査が常にそうしてきたとおり)、索引側の行と合流
させます。索引が持つ行のうち build 以降に変わった行も、変更ログを通して同じように
読みます。

だから build が遅れても、答えは変わりません。変わるのは、各クエリのうち行単位で
読まれる部分が増え、レイテンシが索引なしの数字へ戻っていくことだけです。再 build
の頻度は性能の設定であって、正しさの設定ではありません。既定は毎晩、成長の速い
コーパスなら毎時が目安で、遅れ具合は `status` の `rows_read_exactly` で
いつでも見られます。

**索引が使われない時**。索引が置き換える走査はそのまま残っていて、fallback
です。ファイルが無い、ファイル自身の整合性検査に落ちる、クエリベクトルの幅が
索引と合わない、変更ログがファイルを保証できない (build 以降にログが止まった・
再開した、後の build がこのファイルに要る変更を捨てた、スキーマが変わった)。
これらの時、recall は走査に戻ります (遅いが、正しい)。

いずれも運用者が health を読む場所に報告されます。`check_health` は、索引が
無ければ `vector_index_absent` (カバーできる行数つき)、ファイルが信頼できなければ
`vector_index_unusable`、変更ログがファイルを保証できなければ `vector_index_log_refused`
(`reason` つき) を出します (テーブルごとに 1 行、それぞれ `table` を
名乗ります)。サーバーは走査に戻したクエリごとに warning をログへ出します。

こうしないと、1 週間使えないままだった索引が「なぜか速くならない」としか
見えません。報告はその失敗を防ぐためにあります。

索引の設定項目はありません。パスは `CPERSONA_DB_PATH` から導出され、索引が担う
走査窓は、走査と同じ `CPERSONA_MAX_MEMORIES` です。

## Block の索引ファイル { #the-block-index-file }

`CPERSONA_BLOCK_INDEX=false` にしない限り、Block のアームは想起のたびに SQLite から最大 25 万行を読む代わりに、
3 つ目の派生ファイル `<database>.blocks.blockindex` から行を読みます。答えはどちらでも同じで
([約束 §3](BLOCK_CANDIDATES_CONTRACT.md#3-decisions))、違うのは時間だけです。ほかの 2 つのファイルと
同じく、バックアップせず、修復せず、消してかまわず、削除 (purge) の時も同じ規則で
消されます。

ファイルの大きさは Block の行ごとに 28 バイトと、モデルの次元ごとに 1 ビットです。768 次元のモデルで
124 バイト、1,024 次元で 156 バイトになります。Linux と macOS ではマップするので、想起が読む部分だけを
OS が読み込みます。Windows ではファイル全体をメモリに読みます。使わない場合は `CPERSONA_BLOCK_INDEX=false`
にして再起動します。サーバーは起動時に変更記録を止め、想起は SQLite を読み、ファイルは消してかまいません。

手で作る必要はありません。設定が on の間、サーバーは Block が変わった記録の記録 (変更記録) を付け、
ファイルが無い・使えない・その記録から遅れすぎている時に、起動時と Block を書いた後にキューがファイルを
作ります。作り直しは同時に 1 つだけ積まれます。作り終わるまで、想起は SQLite を読みます。タスクキューを
無効にしている時や、今すぐ作りたい時は次を使います。

```bash
python -m cpersona.block_index --db /path/to/cpersona.db build
python -m cpersona.block_index --db /path/to/cpersona.db status
```

`status` は、今の想起がファイルを読めるか (`current`) と、作った後に変更記録がどれだけ進んだか
(`changes_since_build`) を報告します。ファイルが無ければ 1、あっても使えなければ 2 で終了します。
ある想起がどちらから読んだかを見るには、その trace を求めます (`trace=true`)。`block_source` が `file`、
またはファイルを読まなかった理由つきの `sqlite` を示します
([想起の trace](RECALL_PROCESS_DESIGN.md#12-shape-trace_version-1))。

設定が on の間、`check_health` は `block_index_absent`、`block_index_unusable`、`block_index_behind` を
観察 (info) として報告します。どの想起も SQLite から答えを得ているためです。設定が off の時に出るのは
`block_log_without_index` だけで、(たとえばコマンドラインから作ったために) 変更記録が動いたままになり、
読む者のいない行を Block の書き込みごとに足している状態です。`check_health(checks=["block_index"], fix=true)`
で止まり、設定を off にしてサーバーを起動しても止まります。

## ダッシュボード { #the-dashboard }

`cpersona dashboard` は、記憶のデータベースを読み取り専用のページとしてブラウザで開きます。ページには、保存されている記憶の件数と時期の概要、論理ディレクトリの木 (エージェント・プロジェクト・チャンネル・年・月)、フォルダ・月・本文で絞り込める一覧、各記憶の全文とノード・ブロックへの分割を表示します。

```bash
cpersona dashboard --db ~/.claude/cpersona.db      # または: uvx cpersona dashboard --db …
python -m cpersona.dashboard --db ~/.claude/cpersona.db
```

- **エージェントから開く**: エージェントに、ダッシュボードを開くように頼んでください。stdio のトランスポートでは、サーバーが `open_dashboard` を登録します。このツールは、サーバーがすでに使っているデータベースのページを開いてアドレスを返すので、パスを調べる必要がありません。この開き方では、概要に `check_health` と同じ検査 (修復はしない) によるデータベースの状態も出ます。ページはサーバーが止まるまで動きます。`CPERSONA_DASHBOARD=false` でツールが消えます。HTTP では、次の項目のリモートのダッシュボードを有効にした時だけ登録されます。エージェントのプラグインの `/cpersona:dashboard` は、エージェントにブラウザでページを開かせます。この機械ではツールの `open_browser` で開き、リモートのサーバーでは返ってきたリンクをその場で開くので、リンクを手で写す必要はありません。
- **離れた場所から使うサーバーで** (既定はオフ): `CPERSONA_DASHBOARD_REMOTE=true` にして、`CPERSONA_DASHBOARD_PUBLIC_URL` に人がサーバーに届くアドレスを設定すると、HTTP のトランスポートが `/dashboard/` の下でページを配り、`open_dashboard` も登録します。認証を通ったクライアントが頼むと、このツールは呼ぶたびに新しいリンクを返します。リンクは 10 分以内に 1 回だけ開けます。エージェントがその人のブラウザを開ける時は、自分で開くようツールが伝えます。リンクのコードは `#` の後ろにあるので、要求の行にも、アクセスログにも、Referer にも載りません。ページはこのコードをヘッダで 1 回だけ送り、引き換えにセッションの Cookie を受け取ります (HttpOnly・Secure・SameSite=Strict、`/dashboard/` にだけ送られます)。セッションは 30 日続き、半分を過ぎてから使うと延長されます。そのため、ページのブックマークは、使っているかぎり開けます。アドレスは https か、localhost の http でなければなりません。それ以外の http のアドレスでは、ブラウザが Secure の Cookie を捨てるので、ツールはそのアドレスを拒みます。
  - **誰に何が見えるか**: クライアントの権限で読めるエージェントの分だけです。ほかのエージェントの記憶・エピソード・実体・ブロックは出しません。それらのどれかを指す言及・関係・別名・ノードも出さないので、見えない記録の id はページに届きません。データベースの状態は、すべてのエージェントを読めるクライアントにだけ出します。ACL がない時は、1 本のトークンを持つ人がすべてを見られます。人ごとに分けた接続 (per-subject) からは、まだ開けません。
  - **何に答えるか**: GET と HEAD だけです。`/dashboard/` の外は、末尾の `/` がない `/dashboard` も含めて、これまでどおり bearer トークンが要ります。
  - **セッションは Cookie そのものです。** サーバーが署名し、クライアントの名前と終わる時刻を持ちます。署名にはそのクライアントのいまの bearer トークンも含めます (ACL がない時はサーバーのトークン)。再起動しても続きます。クライアントのトークンを替えるか、クライアントを ACL から外すと、そのクライアントが開いたセッションはすべて終わります。権限は、要求のたびに ACL から読み直します。設定の「ログアウト」で、そのブラウザの Cookie を消せます。署名の鍵は、`CPERSONA_DASHBOARD_SESSION_KEY` を設定していればその値、なければ初めて使う時にデータベースの横に作るファイル (`<名前>-dashboard.key`、所有者だけが読める) です。このファイルを消すと、すべてのセッションが終わります。まだ使っていないリンクはサーバーのプロセスの中にあるので、再起動すると消えます。1 つのクライアントが持てるのは 20 本までで、それを超えると、そのクライアント自身の古いものから消え、ほかのクライアントの分は消えません。
  - **メモリ**: ページのために計算した図は、権限の組ごとにキャッシュします。権限の組が違うクライアントが多いサーバーでは、その数だけキャッシュを持ちます。

- **どのデータベースか**: `--db` で指定したもの、なければ `CPERSONA_DB_PATH`。サーバーの相対パスの既定値には落ちません。端末のフォルダから解決されて、別のファイルを開いてしまうためです。CPersona を MCP クライアントから使っている時は、そのクライアントのサーバー設定にある `CPERSONA_DB_PATH` がそのパスです。
- **何も書きません。** ファイルは SQLite の `mode=ro` で開くので、書き込みは SQLite 自身が拒みます。動いているサーバーの横で開いたままにでき、ページを読み込むたびに最後に確定した状態を読みます。このリリースが知らないスキーマのデータベース (新しいもの、またはスキーマ 19 より古いもの) は、読まずにその旨を出します。
- **誰が見られるか**: 127.0.0.1 だけで、空いているポートで待ち受けます (`--port` で指定できます)。表示されるアドレスには、起動ごとに作るトークンが `#` の後ろに付いています。この部分はブラウザが要求に載せません。データは、このトークンを持ち、Host ヘッダがループバックのアドレスを指す GET の要求にだけ返します。同じ機械の別の利用者は、ポートには届いてもデータは読めません。`--no-browser` は、ブラウザを開かずにアドレスだけを表示します。
- **画面の配置**: 2 つの方式があり、設定 (サイドパネルの下の歯車) で選びます。選んだ方式はブラウザに保存します。既定の「標準」は、1 つのサイドパネルに画面の項目 (概要・記憶・記憶ネットワーク・エピソード・実体・プロフィール) を並べ、その下で論理ディレクトリをたどります。記憶は一覧の横の引き出しで開くので、一覧は動きません。「タブ表示」は、左端にアイコンの列、その右に論理ディレクトリをたどるか検索するサイドパネル、上にタブを置きます。記憶はそれぞれ自分のタブで開き、タブごとに戻る・進むがあります (Alt+← / Alt+→)。方式を切り替えても、開いている記憶はそのまま開いています。どちらでも、Ctrl か ⌘ と K・O・P のどれかで、コマンドパレットが開きます。
- **検索**は、タブ表示のサイドパネルで行います。入力したすべての語を本文に含む記憶を探し、一致した行を表示します。`"語句"` は書いたとおりに一致し、`-語` はその語を含む記憶を除きます。`path:` はエージェント/プロジェクト/チャンネル、`agent:` はエージェント、`tag:` は記憶が言及する実体の名前か別名、`line:` は同じ行にそろう語、`month:` はタイムスタンプの先頭 (`month:2026-10`) に一致します。`[locked]`・`[recalled]`・`[vector]` は、ロックされた記憶・想起されたことのある記憶・ベクトルを持つ記憶だけを残し、`[project:x]` と `[channel:x]` は、そのプロジェクトかチャンネルにちょうど一致する記憶だけを残します。Aa で大文字と小文字を区別し、パネルの設定で結果を新しい順・古い順・想起の多い順に並べられます。
- **記憶ネットワークは記憶を描きます。** メモアプリのグラフがすべてのノートを描くように、すべての記憶を 1 件ずつ点にします (2 つ後の項目)。リンクから開いた時は、フォルダ・月・実体・内容の近いまとまりの記憶だけを描きます。
- **見た目**: 暗い背景の上で、記憶は小さな無地の点、エージェントは模様 (縞・三日月・輪・点・四分割) の入った平らな点で描きます。模様は id から決めるので、同じエージェントは読み込むたびに同じ見た目です。色を付けるのは、指している点とその線だけです。「エージェントで色分け」を入れると、エージェントごとに色を付けます。エージェントの名前は常に出し、ほかの名前は拡大するにつれて出てきます。点が 1,000 を超える図では、点を線の上に明るく描きます。設定の「集合体回避モード」を入れると、点を小さく淡くして線を主役に描きます。点が密に集まった画面を見ると不快になる人のための設定です。
- **記憶**は、点にして 3 種類の線で結びます。線は種類ごとに隠せます。1 つ目は、エージェントが宣言した関係です (記憶が言及する実体と、実体や記憶のあいだの関係)。2 つ目は、内容が似ている記憶です。保存された埋め込みのコサインが 0.55 以上のうち、近い順に 3 件まで結びます。この線はサーバーが計算したもので、エージェントが宣言したものではありません。3 つ目は、エージェントとその記憶を結ぶ線です。フォルダの図は、メモアプリがすべてのノートを描くように、フォルダの記憶をすべて描きます。近い記憶は 1,024 行ずつ探すので、一度に持つ類似度はフォルダの件数の 2 乗ではなく件数に比例して増えます。ページには記憶の本文を送らず、点を選んだ時にその記憶の本文を取りに行きます。点が 1,000 を超える図では、点どうしの押し合いを Barnes–Hut でまとめて計算し、エージェントとその記憶を結ぶ線を最初は隠しておきます。最初の 1 枚を描く前には、何も落ち着かせません。前に見た図は前の位置のまま描き、新しい点だけが、ほかの点を止めたまま画面の上で落ち着きます。初めての図は画面の上で落ち着かせ、その間に枠を合わせます。サーバーは、閲覧者ごとに、フォルダの最後の図を保持します。データベースがその後に変わっていたら、保持している図をすぐに返し、新しい図は次の要求のために裏で計算します。そのため、少し前に保存した記憶が、1 回だけ図に入らないことがあります。保持している図は、少なくとも 10 分ごとに計算し直します。概要を読んだ時に、データベース全体の図を裏で計算し始めるので、記憶ネットワークを開く頃には、たいてい用意できています。ページの側も、開いたらすぐにデータベース全体の記憶ネットワークを取得し、最近取得したいくつかを手元に持っておきます。記憶ネットワークを開くと、持っている図をすぐに描き、描いた裏で取り直して、次に開く時に使います。記憶の「記憶ネットワークで見る」は、その記憶から、似ている記憶をたどって 2 段先までを、データベース全体から描きます。ベクトルは同じ幅のベクトルとだけ比べます。データベースの行が変わらないあいだは、最大 5 分、ダッシュボードを動かしているプロセスに保持します。ページには送りません。ベクトルの合計が 128 MB を超えるデータベースは保持せず、たどるたびに少しずつ読みます。
- **点は、置かれた場所にとどまります。** 点の最初の位置は記憶の id から決めるので、同じデータは読み込むたびに同じ形で描かれます。落ち着いた位置は、最近開いた 20 の図についてブラウザに保存します。次に読み込む時はそこから始め、そのあとに増えた点は、つながっている点のそばから始めます。落ち着くまで動くのは新しい点だけです。位置は、データベースのファイル名と図ごとに、そのブラウザの中にだけ保存します。
- **エピソードと実体**は、記憶と同じように一覧から開きます。標準の方式では引き出しで、タブ表示ではそれぞれのタブで開きます。エピソードは新しい会話から順に並び、要約とキーワードで検索できます。開くと、会話の時間、話題が決着したかどうか、そのエピソードで言及していると宣言された実体が出ます。実体は言及の多い順に並び、名前と別名で検索できます。開くと、その実体に言及している記憶・エピソードと、その実体が加わる関係が出て、それぞれをそこから開けます。関係が指す記録が読めない時 (閲覧者に見えない範囲にあるか、もう無い時) は、中身を出さずに「見つかりません」と表示します。
- **プロフィール**は、エージェントが利用者についてまとめた要約です。エージェントごとに全文を、書いた日時と、書き込みで切り詰められる上限に対する長さとともに表示します。エージェント自身のプロフィールは想起のたびに答えに付きます。利用者を指定して書いたものは、付かないことを表示します。記憶の一覧でエージェントを選ぶと、そのエージェントのプロフィールを記憶の上に表示します。
- 想起の trace はまだ表示しません。ページから編集することもできません。データベースの状態は、エージェントから開いた時だけ出ます。端末から開いたダッシュボードは、ファイルだけではそれを判定できないためです。

## メンテナンスの頻度 { #maintenance-cadence }

- **月次**: `check_health(agent_id, fix=true)` で決定的な整合性チェックと
  自動修復、`deep_check(agent_id, fix=true)` で意味の面の検査、加えて
  `export_memories` による論理バックアップ。
- **コーパスの大変動の後** (一括インポート、再構築、モデル変更):
  `calibrate_threshold(agent_id)`。
- **ベクトル索引を使っているなら timer で**:
  `python -m cpersona.vector_index build` (既定は毎晩)。build が遅れた時の代償
  (レイテンシであって、正しさではない) は
  [連続ベクトル索引](#the-contiguous-vector-index) を参照してください。
- **バージョンアップ**: スキーマは自動で前方へマイグレーションします。較正には
  スコアリング関数と埋め込み次元の fingerprint が記録されており、どちらかが
  変わると初回起動時にサーバーが再較正します (v2.5.2 以降)。
