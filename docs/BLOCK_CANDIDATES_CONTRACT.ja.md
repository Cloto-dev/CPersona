# Block の候補生成 — 約束 { #block-candidate-generation-contract }

> **翻訳について**: 正本は英語版です。日本語版が古い場合は英語版を参照してください。

Status: 約束、その適合検査のデータ、そのデータで検査した Go の実装が `master` にあります。
サーバーはまだ Go の実装を呼ばず、どのリリースにも含まれていません。想起の答えは変わりません。

## 0. これは何か { #0-what-this-is }

Block の腕 ([Block による到達](BLOCK_REACH_DESIGN.md)) は、すべての記録を節の大きさに分けた Block を、
1 次元 1 ビットの Hamming 距離で探します。その探索は 2 つに分かれます。

1. **候補生成。** 1 回の呼び出しで見てよい Block の行を読み、それぞれの問いへの Hamming 距離を測り、
   書き下された順序で近いものをいくつか残します。
2. **並べ直し。** 残した行の保存済みベクトルを読み、cosine で並べ直します。

前半が返すのは整数と識別子だけなので、別の言語の実装に「同じ行を同じ順で返すこと」を厳密に求められます。
このページは前半を約束として書き、その実装をどう検査するか、そしてその実装をどこで動かし、どう配るかを記録します。

**Block の母集団から始める理由。** 実際の長さの記憶 10 万件では、Block は 3,480,069 行、1 記録あたり
34.8 行あります
([コーパス](https://github.com/Cloto-dev/CPersona/blob/master/benchmarks/measurements/results-recall-latency-realistic-corpus.md))。
そのため Block は記録 約 2.9 万件で 100 万行に届き、記録そのものよりずっと早く届きます。
今の想起の時間を決めているのは候補生成ではなくキーワードの腕です (第 4 節)。この段の理由は規模です。

## 1. 約束 { #1-the-contract }

**入力。**

- **行**。キーの順 (種類のバイト順、次に親の id、次に Block 番号) に並んでいます。各行は種類・親の id・
  Block 番号、記録の agent id・project id・channel、ビット列を作ったモデルのラベル、そしてビット列
  (まだ無ければ無し) を持ちます。
- **問い**。ビット列、agent id、project id (無し・空・名前のどれか)、channel (空・名前のどちらか)、
  2 つのモデルのラベル。
- **3 つの上限**。見てよい行の数、そのうち 1 記録が取ってよい数、返す行の数 (深さ)。どれも、
  呼び出し側が受け取りたい件数からは導きません。

**手順。** 規範です。どこか 1 段でも違う実装は、違う行を返します。

1. **受け入れ。** ビット列があり、ラベルが 2 つのモデルのラベルのどちらかに等しく、agent id が問いと
   等しく (空の agent id は「名前のあるエージェントが持たない行」の区分で、ワイルドカードではありません)、
   下の 2 つの軸が許す行を受け入れます。受け入れない行は、どちらの上限も使いません。
   - **project。** 無しはすべての project を読みます。空は全体の共有分 (project id が空の行) だけを
     読みます。名前はその project と全体の共有分を読みます。
   - **channel。** 空はすべての channel を読みます。名前はその channel と、channel 共通の行
     (channel が空の行) を読みます。
2. **調べる。** 受け入れた行をキーの順にたどります。1 記録の取り分は、Block 番号の順で先頭から
   1 記録の上限までで、それより後の行は飛ばします。調べる上限が満ちたら止まります。取り分は受け入れた
   行で数えるので、ビット列の無い行や別のラベルの行は、記録の取り分を使いません。
3. **測る。** ビット列の長さが問いと違う行には距離がありません。取り分と調べる上限の 1 枠は使いましたが、
   順位には入りません。幅が違えば次元が違い、その間の距離は意味の無い数になるからです。
   それ以外の調べた行には、問いへの Hamming 距離を付けます。
4. **並べる。** 測った行を、距離、種類、親の id、Block 番号の昇順に並べます。キーは一意なので、
   2 つの行が同点になることはありません。深さまでの先頭の行を返します。

**出力。** 返す行ごとに、種類・親の id・Block 番号・距離。本文もメタデータも浮動小数のスコアも返しません。

**サーバーに残るもの。** 保存済みベクトルによる並べ直しと、その後に続く処理は Python のサーバーに残ります。
別の順で足した cosine は別の浮動小数になり、想起の順はその浮動小数で決まるので、並べ直しは別の言語で
サーバーの答えに厳密に合わせられません。返す行にまだ保存済みベクトルが無い時 (ベクトルを作っている
途中の配備) は、その呼び出しを今と同じくサーバー自身の経路で答えます。

## 2. 適合検査 { #2-conformance }

**golden。** `tests/golden/block_candidates.json` が場面を持ちます: キーの順の行、問い、上限、そして
返るべき行。これを書くのは `scripts/capture-block-candidates.py` で、想起が使う関数
(`blocks._examined`、`blocks._measured`、`blocks._order`) を本物のデータベースの上で走らせます。
返るべき行を手で書く人はいません。行は順不同で挿入するので、答えは表のキーで決まり、届いた順には
左右されません。

**場面が覆うもの。** 768 次元のモデルの幅と想起そのものの上限。深さの切れ目が同じ距離の並びの中に
落ち、書き下された順だけが決める場面。それぞれの上限が効く場面と、両方が同時に効く場面。記録の中で
受け入れられない行 (ビット列が無い、別のモデルのラベル) と、幅の違う行 (狭いものも広いものも) が
並ぶ場面。3 つの軸のすべての読み方。測った行が深さより少ない場面。そして空の答え。

**Python 側の 2 つのテスト。** `tests/test_block_candidates_golden.py` は、ファイルがコードの返すものと
違ってきた時と、場面がこのページの名指す規則を検査しなくなった時 (たとえば、切れ目が同点の中に落ちる
場面が無くなった時) に失敗します。サーバーのコードを壊すと (同点の順序、1 記録の上限を 1 つずらす、
ビット列の無い行を受け入れる、幅の検査を緩める) 1 つ目のテストが失敗します。

**Go 側。** `go/blockcand` が同じファイルを読みます:

- その実装は、すべての場面で行を順どおりに返します。
- 何も返さない実装は、行を期待する場面でちょうど失敗するので、検証役は答えの欠落を報告します。
- わざと壊した実装の組 (各上限をどちらかに 1 つずらす、同点の順序をどちらかに変える、ビット列の無い
  行を受け入れる、別の幅の行を拒む、ラベルや agent を無視する、各軸を広く・狭く読む、取り分をすべての
  行で数える) は、どれも少なくとも 1 つの場面で失敗します。

壊したサーバーから作り直した golden では Go のテストが失敗します。だからサーバーの候補生成の変更は、
他のすべての実装が追いつかない限り golden に届きません。

## 3. 決定 { #3-decisions }

### 3.1 サーバーの中のライブラリでなく、別のプロセス { #31-a-separate-process-not-a-library-in-the-server }

Go の実装は、Python のプロセスに読み込む共有ライブラリではなく、サーバーがローカルのソケットで問い合わせる
sidecar プロセスとして動きます。

- PyPI のパッケージは pure Python のままで、プラットフォームごとの wheel を作り続ける必要がありません。
- サーバーは埋め込みサーバーとすでにこの形で動いており、派生した索引が無い時の経路 (サーバー自身の
  保存から答える) もすでにあります。sidecar が無い・失敗する時も同じ経路を通ります。
- 後でサーバー自体が Go に移れば、この境界は 1 つのプロセスにまとまり、ここで書いたものは捨てずに済みます。

代償は、呼び出しごとのローカルの往復 1 回です。

### 3.2 SQLite でなく、Block のビット列の連続ファイルを読む { #32-it-reads-a-contiguous-file-of-block-bits-not-sqlite }

sidecar は Block のビット列を、SQLite のデータベースからではなく、サーバーが書く連続ファイルから読みます。

Intel N150 で実際の長さの記憶 10 万件に対し、代用の問いベクトルで取った登録外の内訳では、Block の腕は
654 ms で、そのうち 468 ms が調べる行を SQLite から読み出す時間、128 ms が測る時間、23 ms が並べ直しの
ベクトルを読む時間でした。同じ行を別の言語で SQLite から読む実装は、その費用の大半を残します。
ファイルは記録の粗探索の索引
([1 ビット粗探索 §3](BINARY_COARSE_SEARCH_DESIGN.md#3-the-coarse-index)) にならいます:
サーバーが書き、開く時に検証し、watermark より後の行は保存から読みます。

記録との違いが 1 つあり、設計が要ります。キーは種類から始まるので、ファイルを作った後に書かれた Block は、
ファイルのどの行よりも後ろに並ぶとは限りません。episode の Block はどの memory の Block よりも前に並びます。
上限はキーの順で切るので、watermark より後の行は、どちらの上限を当てる前にもキーの順へ混ぜ込む必要があります。

**得られるもの (はっきり書くと)。** 同じファイルを numpy で読めば、Go が無くても SQLite の費用の大半は
消えます。今の上限のままでは、Go で読むこと自体の利得は小さく、それは規模での利得です。調べる上限
(25 万行) は 10 万件ですでに効いていて、1 回の呼び出しが見るのは Block の約 7%、キーの順で先頭のものです。
この上限を外すと腕が届く記録が変わるので、答えの質で測る別の決定であり、この約束には含めません。

### 3.3 cgo を使わない { #33-no-cgo }

モジュールは `CGO_ENABLED=0` で建つので、1 台のマシンですべての対象を建てられます:
linux/amd64 (`GOAMD64=v2`)、linux/arm64、darwin/arm64、windows/amd64。sidecar が C のドライバで
SQLite を読まない理由の 1 つもこれです。

### 3.4 配り方 { #34-shipping }

- Go のモジュールはこのリポジトリの `go/` に置きます。約束、golden、両方の実装の変更が 1 つの
  pull request に入り、複数のリポジトリで歩調を合わせ続ける必要がありません。
- 実行ファイルは GitHub Releases に添付します。
- PyPI のパッケージは pure Python のままで、実行ファイルを必要としません。無ければ、想起は今と同じに答えます。
- 実行ファイルを `pip` で運ぶ別のパッケージは、配備から求めがあれば後から出すかもしれません。

### 3.5 既定は off、答えは変わらない { #35-off-by-default-answers-unchanged }

sidecar を出す時は、使う側が明示して有効にします。sidecar が無い、ファイルが壊れている、次元が違う時は、
呼び出しをサーバー自身の経路に送ります。sidecar には「答えがどこまで悪くなってよいか」の上限ではなく、
この約束と golden によって、その経路と同じ行を同じ順で返すことを求めます。

## 4. この段に含めないもの { #4-not-in-this-step }

- **ファイルの形式、sidecar の通信手順と退避経路、リリースの実行ファイル。** 次の段です。
- **調べる上限を外すこと。** 答えの変更なので、それだけで測ります。
- **記録の粗探索。** 同じ仕組みを別の母集団に当てるもので、記録の件数が見合うようになってからです。
- **並べ直し。** 第 1 節の理由で、予定していません。
- **キーワードの腕。** 同じ内訳で想起のいちばん遅い腕はキーワードの腕、つまり SQLite の中の全文検索の
  順位付けで、この段は触りません。
