# 証拠の配分 — 設計 { #evidence-allocation-design }

> **翻訳について**: 正本は英語版です。日本語版が古い場合は英語版を参照してください。

Status: 2.6.5 に向けた設計です。最初の pre-release (2.6.5a1) は、レコードをまたいで並べた引用の列
(第 3 節と第 4 節) を `CPERSONA_RECONSTRUCT_SEQUENCE=evidence` として既定 off で出荷しました。
2.6.5a3 は、同じ順序にレコードの長さで引いた床を付けた列 (`whole`、第 4 節の末尾) を、
これも既定 off で足し、それを 2,800 字で使う `reconstruct` の `lite=true` を加えます。第 5 節の被覆の段は
`whole` の上に作り、両パックの判定用の問いで判定して、採りませんでした。どの段も、回答の呼び出しより前に
登録した判定則で測ります (第 7 節)。`SCHEMA_VERSION` は変わりません。以下はすべて、ストアが
すでに持っている Block と Block ごとの int8 ベクトルを読みます。

## 0. この段階は何か { #0-what-this-step-is }

`reconstruct` は、1 本の固定された列を予算で切って item を返します
([第 7 節](RELIABLE_RECALL_2_6.md#breadth-before-depth-the-payload-budget))。列は、すべての先頭引用を
item の順に並べ、そのあと各 item の抜粋を順に回したものです。v1.2 からは、先頭引用はそのレコードの
一致した部分で、大きさは item の位置で決まります — 最初の 5 件は 800 字、それ以降は 400 字です。
予算はこの列の先頭をどこまで返すかだけを選ぶので、予算を上げて何かが消えることはありません
(不変条件 9)。

小さい予算をどう使うかを決めているのはこの列で、列は予算を窓の中の位置に使い、証拠には使っていません。
この段階は、引用する部分を、窓のすべてのレコードをまたいで答えを含んでいそうな順に並べ、その順序を切ります。

## 1. 先に測ったこと { #1-what-was-measured-first }

OmniMemEval の LongMemEval-S (500 問、v1.2、同じ検索) での 4 つの計器が、この変更がすべきことを決めました。

| 測ったこと | 結果 |
| --- | --- |
| 末尾から item を減らす ([件数曲線](https://github.com/Cloto-dev/CPersona/blob/master/benchmarks/measurements/results-omnimemeval-lme-count-curve.md)) | 4 件で 994.6 Context Tokens・77.00%。全件では 1,786.7・81.60%。複数セッションの問いが最も落ちる |
| すべての引用を短くする ([引用長の曲線](https://github.com/Cloto-dev/CPersona/blob/master/benchmarks/measurements/results-omnimemeval-lme-quote-curve.md)) | 同じ費用では、測った 2 点ともに item を減らす方に負ける。4 件より 7.40 ポイント、6 件より 4.20 ポイント低い |
| 文脈が何を引用しているか ([証拠の指標](https://github.com/Cloto-dev/CPersona/blob/master/benchmarks/measurements/results-omnimemeval-lme-evidence.md)) | 全件では正解セッションの 96.2% を引用するが、引用した本文のうち正解セッション由来は 21.9% だけ。500 問中 426 問で最初の item が正解セッションを持つ |
| 短い引用はどこで証拠を失うか | 引用されたレコードの中にありながら引用の外に残る証拠の発話は、320/160 字で 7.5% から 23.3% に増える。長すぎる範囲を切ったために失われたものは 0 |
| 証拠はレコードの中で何位か | 引用された正解レコードの証拠の発話 859 のうち、レコードの中で最上位の範囲が届くのは 62.9%。2 位 16.3%、3 位 6.3%、4〜5 位 6.4%、それ以下 8.1%。サーバーの順位付けで計算し直したもので、引用範囲 5,888 件をすべて再現した |

この設計が拠って立つのは最後の 2 行です。答えている発話は、そのレコードの最上位の範囲でないことが
多い。長い引用は 2 位・3 位の範囲まで埋めてそこに届き、短い引用は届きません。もう 1 つの一様な切り方で
ある item の削減は、複数セッションの問いが必要とする 2 つ目のセッションを失います。どちらの切り方も
証拠を見ていません。

## 2. 引用の候補 { #2-candidate-passages }

引用の候補は、窓の中のレコードの Block を、それを支配する範囲 (`blocks.context_range`: その Block が
属する文と、それを修飾する隣) まで広げたものです。すべての item のすべてのレコードが Block を出します。
現在の Block の集合を持たないレコードは、今と同じく読み出し時に分けた部分を出します。1 つのレコードの
中で重なる範囲は、順位を付ける前に 1 つにまとめるので、同じ本文が 2 度候補になることはありません。

## 3. レコードをまたいだ 1 つの順序 (2.6.5a1) { #3-one-order-across-records-265a1 }

今の `rank_blocks` は 1 つのレコードの Block を並べます。ここでは、すべてのレコードのすべての候補を、
3 つの順位の reciprocal-rank fusion で 1 つの順序に並べます。

- 窓を作った recall でのレコードの順位
- レコードの中での候補の順位 (今の `rank_blocks` の順)
- 保存済みの int8 ベクトルと問いのベクトルの cosine による、全候補の中での順位

同点は、レコードの順位、次に本文の中の位置で決めるので、順序は全順序で決定論的です。スコアは返しません。
trace に各候補の 3 つの順位を記録します。

1 つのレコードの中だけで見ると、この順序が `rank_blocks` と違うのはベクトルに余分な重みを与える点だけです
(レコードの順位はそのレコードのすべての候補で同じ)。使い道はレコードをまたぐことなので、今の列の中では
なく、第 4 節の引用の列として測ります。

## 4. 引用の列 (2.6.5a1) { #4-the-payload-sequence-265a1 }

引用の列は、第 3 節の順に並べた候補になり、予算には依りません。予算はこの列を今の列と同じように切ります。
応答は、収まる最長の先頭部分です。不変条件 9 は形を保ちます — 予算は先頭部分を選ぶだけなので、予算を
上げて引用が消えることはありません — が、その前半は変わります: **列は、もはやすべての先頭引用を抜粋より
前に置きません**。1 件目のレコードの引用が 10 件目のレコードの唯一の引用より前に来ることがあり、小さい予算
では、より少ない item をより多く返すことがあります。第 1 節がその理由です: 同じ費用では、すべての item を
薄く保つ方が、少ない item を丸ごと保つより多くを失いました。

応答の形は変わりません。item は今もレコードごとに 1 つで、recall の順に並びます。item の `content` は、
その先頭レコードのうち切り取りに入った候補を本文の順に並べ、今の先頭引用と同じようにつないだものです
(`ranges` が範囲を示します)。`excerpts` は今まで通り item の他の claim を引用します。予算の中に候補が
1 つも入らなかったレコードの item は返さず、そのことは今と同じく報告します。`count` の意味 (item 数の上限)
は変わりません。trace は列と、各候補の順位 (第 5 節を実装した後は押さえた部分も) を記録します。

### レコードの長さで引いた床 (2.6.5a3) { #a-floor-by-record-length }

非公開の実運用パックの調整用の問いでは、第 3 節の順序が、今の列なら残せた答えを落としました。予算は
先頭のレコードの 2 つ目・3 つ目の候補に使われ、そのあと落ちた item は答えを持つ短いレコードでした。
落とした証拠の多くは、引用 1 つ分以下の長さのレコードにありました。レコードが 1 つのセッションで、答えが
たいてい 1 件目の item にある LongMemEval-S では、同じ順序の方が良い結果でした。

`CPERSONA_RECONSTRUCT_SEQUENCE=whole` は順序を保ったまま、その前に長さで引いた床を置きます。引用の長さ
(`CPERSONA_RECONSTRUCT_QUOTE_CHARS`) 以下の先頭レコード — 第 2 節がすでにレコードそのものを 1 つの候補と
して扱うもの — が item の順に列の先頭に並び、それより長いレコードの候補が第 3 節の順で続きます。短い
レコードの費用はその本文の長さを超えません。予算はこれまで通り先頭部分を切るので、予算を上げて引用が
消えることはありません。

同じ調整用の問いで、ほかに 2 つの床を測って採らないことにしました。すべてのレコードの最良の候補を先に
置く床は、長いレコードのそれぞれに 1 候補ずつ予算を使いました。実運用パックでは長いレコードの 2 つ目の
候補にあった答えを落とし、LongMemEval-S では順序が先頭のレコードに与える深さを失いました。引用 2 つ分の
長さまでのレコードも (引用 1 つ分の候補まで) 床に入れる案は、床の外に残った最も長いレコードを、床の中の
下位のレコードが上位から押し出しました。

調整用の問いでは、`whole` は両方のパックの測ったすべての予算で、`evidence` 以上の証拠を見せました。
実運用パックでは、多くの予算でまだ今の列より少ない証拠しか見せていません。床より後ろに回るものの中に、
今の列が上位で引用する、引用 1 つ分から 2 つ分の長さのレコードがあるためです。`evidence` の意味は変えず、
`whole` は別の値です。既定は変わりません。

## 5. 被覆 (判定済み、不採用) { #5-coverage-265a2 }

被覆の段は作って `whole` と比べて判定し、出荷していません。`whole` の列を、やはり予算に依らない貪欲法で
作り直すものでした。

1. `whole` の順序 (第 4 節) から始める。
2. 最初の passage を取る。それが押さえる問いの部分に印を付ける。部分とは被覆台帳の部分、つまり
   `trace.coverage` が記録する問いの語 (2 文字以上の漢字・カタカナの連なり、または ASCII の識別子。
   NFKC と小文字化の後) で、その passage 自身の範囲の中に見つかるものです。
3. 残りの passage を、その順序での位置に置いたうえで、これまでに取った passage が押さえていない部分を
   押さえるものは 5 つ上げ、押さえる部分がすべて押さえ済みのものは 5 つ下げて、最初のものを取る。
   部分を 1 つも押さえない passage は位置を変えず、同点は前の位置が勝つ。すべての候補が並ぶまで繰り返す。

item の順で最初の 2 レコードの passage は下げませんでした。答えがあるのはたいていそのレコードで、
同じレコードの 2 つ目の passage は、同じ事柄について書いているので問いの語を繰り返すからです。

非公開の実運用パックの調整用の問いでは、測ったどの予算でも `whole` より多くの根拠を見せ (2,800 で
113 対 104)、LongMemEval-S の調整用の問いでも正解のセッションを同じかそれ以上の割合で見せました。
そこでほかに 3 つの順序を採りませんでした。今の列のように各レコードを item の順に先頭引用の大きさまで
先に埋める順序は、実運用パックで最も多くの根拠を見せましたが、レコードがセッションである
LongMemEval-S では 4 件分のセッションにしかならず、正解のセッションを見せた割合は 4 件と同じでした。
最初の 2 レコードだけをそのように先に埋める順序は、下げないだけの規則と並び、最初のレコードを下げない
ことをせずに動かすと少なく見せました。

登録した判定では、調整での差は残りませんでした
([結果](https://github.com/Cloto-dev/CPersona/blob/master/benchmarks/measurements/results-omnimemeval-lme-v1_5-coverage.md))。
非公開パックの判定用 150 問、予算 2,800 で、`coverage` は 196 の根拠の引用のうち 121 を見せ、`whole` は
120 でした。見せた字数をそろえた今の列より 2 少なく、予算 2,000 と 4,000 では `whole` より 7 と 2 多く
見せました。LongMemEval-S の判定用 400 問では 319 問の文脈を変え、正解のセッションを `whole` とほぼ同じ
割合で見せました (95.5% 対 95.7%)。見せた字数をそろえると、実運用パックでは今の列、`whole`、`coverage` が
数件の範囲に並びます: 短いレコードを守った後では、窓の passage を問いの語で並べ直しても、見せる根拠は
あまり動きません。`lite=true` の列は `whole` のままです。

## 6. 変わらないこと { #6-what-does-not-change }

モデルは呼びません。content は保存された本文の引用です。結果は決定論的です。すべての候補はそのレコードの
参照を持ちます。スキーマ、窓を作る recall、`count` の意味は変わりません。

## 7. 判定の仕方 { #7-how-it-is-judged }

- **主**: Context Tokens が 1,000 以下になる予算で、4 件 (994.6 で 77.00%) との正答率の対の差の 95%
  bootstrap 区間の下限が 0 より上 — 同じ費用で今より良い。
- **副**: 全件 (81.60%) に対して下限が −2.0 ポイント以上。件数曲線の規則です。
- **調整用と判定用を分けます。** 設定は、非公開の実運用パックの調整用の問いと、固定した乱数で 1 度だけ選んだ
  LongMemEval-S の 100 問
  ([`v1_5_dev_questions.json`](https://github.com/Cloto-dev/CPersona/blob/master/benchmarks/omnimemeval/v1_5_dev_questions.json))
  で選び、主張は残りの 400 問で 1 度だけ測ります。
- どの点でも証拠の指標を正答率の横に報告し、対照 (4 件、6 件、全件、引用長の曲線の 2 点) は記録済みの
  回答を使い回します。
- **`whole` と `evidence` の比較**は、2.6.5a1 の判定と同じ予算で、同じ LongMemEval-S の判定用 400 問と、
  非公開パックの判定用の問いについて、
  [`prereg-omnimemeval-lme-v1_5-whole.md`](https://github.com/Cloto-dev/CPersona/blob/master/benchmarks/measurements/prereg-omnimemeval-lme-v1_5-whole.md)
  に登録した規則で判定します。
- **`coverage` と `whole` の比較**も同じように、同じ予算で
  [`prereg-omnimemeval-lme-v1_5-coverage.md`](https://github.com/Cloto-dev/CPersona/blob/master/benchmarks/measurements/prereg-omnimemeval-lme-v1_5-coverage.md)
  に登録しました。先に走らせた非公開パックの判定は規則を満たさず、LongMemEval-S の回答の段は走らせて
  いません (第 5 節)。

## 8. 後回しにしたこと { #8-deferred }

- 被覆のために問いを節に分けること: 台帳の字句の部分を使った第 5 節の被覆の段は、見せる根拠を動かさな
  かったので、細かい分け方にはまだ測った理由がありません。
- 問いに応じて変わる予算 (想起の設計の第 7 節は、固定方針が再現できる基準と監査の契約を持つまで適応を
  後回しにします。この設計がその固定方針です)。
- Block より細かい証拠の単位と、埋め込みサーバーからの sparse や late-interaction のスコア。
