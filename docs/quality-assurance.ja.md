# 品質保証 { #quality-assurance }

このページでは、cpersona のリリースが出る前に通る検査を説明します。読み手として想定しているのは、大切なコーパスをこのサーバーに預けてよいかを判断しようとしている人と、自分の変更がどの検査を通ることになるのかを知りたいコントリビューターです。

プルリクエストを出す前に検査を**実行する**方法を探しているなら、短くまとめたものが
[CONTRIBUTING § The gates](https://github.com/Cloto-dev/cpersona/blob/master/CONTRIBUTING.md#the-gates)
にあります。

## 監査を通したリリース { #audit-gated-releases }

リリースを切る前に、コードベースは多エージェントによる監査ラウンドを何周か通ります。観点ごとに独立した finder を立て、各 finding をさらに複数の観点から敵対的に検証することで、「もっともらしいが誤っている」報告が修正の段階まで残らないようにしています。v2.4.39 はそうしたラウンドを 3 周してから出荷しました。43 件を修正し、そのすべてを、修正が入ったあとのツリーで再検証しています。

監査が出すのは finding であって、修正ではありません。検証で残った finding は、何かを編集する前に、番号を付けてバグ登録簿に登録します。こうすることで、`bug-NNN` が何を指すかについて、コミットと登録簿が食い違わなくなります。

## バグ登録簿 { #the-bug-ledger }

監査済みの欠陥はすべて
[`qa/issue-registry.json`](https://github.com/Cloto-dev/cpersona/blob/master/qa/issue-registry.json)
に、機械で検査できるコードパターンとともに記録されます。欠陥の中身、再現する条件、何で直したかが残ります。

[`scripts/verify-issues.sh`](https://github.com/Cloto-dev/cpersona/blob/master/scripts/verify-issues.sh)
は登録簿をツリーと突き合わせ、修正の印が消えたり、取り除いたはずの欠陥が戻ってきたりすると、目に見える形で失敗します。これは read-only のインフラです。登録簿を検証するためのもので、検査を通すために書き換えるものではありません。

## 構造 CI ゲート { #structural-ci-gates }

不変条件の中には、通常のテストでは表現できないものがあります。それが 1 つの挙動の性質ではなく**すべての**呼び出し箇所の性質だからです。そうした不変条件は、pytest スイート内の AST レベル / 挙動レベルのゲートによって強制され、Python 3.11 と 3.13 の両方で実行されます。

- すべての writer が共有書き込みロックを保持していること
- agent スコープの SQL が isolation 述語を伴っていること
- identity / dedup のプローブが project 軸と channel 軸を伴っていること
- `check_health` がロック保持中に embedding のネットワーク I/O を行わないこと

この種のゲートは、ルールが抜けた呼び出し箇所そのものを指して失敗します。そこが「たまたま今日の呼び出し箇所を網羅しているテスト」との違いです。

## ドキュメントに書いた事実の検査 { #documented-facts-are-gated-too }

手で書いた数値はやがて古くなります。ドキュメントに書かれたスキーマバージョン・環境変数の既定値は、それを定義しているソースと突き合わせて検査されます。コードと食い違ったドキュメントは、読み手を誤らせる前に CI で落ちます。

ツールの総数はそもそも書けないようにしています。検査が届くページでは常に正しかったのに、届かない場所 (リポジトリの説明文、レジストリに固定されたバージョンごとのコピー) でだけ古くなっていたため、今は総数を書いた記述そのものを検査で落とします。バージョンの主張はリリースタグと突き合わせて検査されます。

日本語ページは翻訳元の英語コンテンツと突き合わせて検査されるため、翻訳が原文から遅れても、気づかれないままにはなりません。さらに、すべてのページと nav のラベルは、翻訳を持つか「英語のままにする」と宣言するかのどちらかでなければなりません。そのため、新しいページが翻訳済みのサイトから気づかれないまま漏れることもありません。

これらのゲートは
[`scripts/`](https://github.com/Cloto-dev/cpersona/tree/master/scripts)
にある `check-docs-facts.py`、`check-doc-anchors.py`、`check-i18n-drift.py`、`check-i18n-coverage.py` です。

## ミューテーション証明 { #mutation-proof }

スイートが緑であることは、テストが走ったことの証明であって、テストが何かに気づいたはずであることの証明ではありません。isolation とロックの不変条件を支えている箇所は CI で意図的に変異させ、変異ごとにスイートが赤になることを証明として求めます。変異させても緑のままのゲートは、合格ではなく**ゲート側の穴**として報告されます。

## リリースライフサイクル { #release-lifecycle }

リリースプロセス自体は
[RELEASE_LIFECYCLE_STANDARD](RELEASE_LIFECYCLE_STANDARD.md) (v1.0) で規定されており、Cloto 系プロジェクトのリファレンス実装としてここで試行されています。どの系列を運用すべきか、その系列がいつまで修正を受けるかは
[SUPPORT.md](https://github.com/Cloto-dev/cpersona/blob/master/SUPPORT.md)
にあります。

## 数字で見る { #by-the-numbers }

- **~45,284 LOC** の Python (機能ごとに分割されたモジュール群)、加えて 4,334 行の vendored MCP common スナップショット
- **~4,144 test functions** / ~317 test modules — 挙動マトリクスをパラメータ化すると ~5,872 cases (~110,541 LOC、サーバーコードよりテストコードの方が多い)。上記の構造強制ゲートを含む
- **Schema v21** (自動マイグレーション)
- **MIT License**

これらの数値は意図して概数にしており、これらも検査の対象です。CI でツリーから測り直し、読み手を誤らせるほどずれた時点で失敗します。
