# 手元のサービス

> **翻訳について**: 原文は英語版です。日本語版が古いときは英語版を参照してください。

- **状態**: 2.7.0a1。stdio の入口は、既定でサービスへ中継します。
  `CPERSONA_LOCAL_SERVICE=off` を設定すると、2.7.0b1 までは以前のプロセス内のサーバーが動きます。
  2.7.0b1 でこの経路は消します。
- **範囲**: stdio で起動された時に、記録先ごとに 1 つのサーバーを探すか立ち上げる方法、
  そのサーバーが受け付けるもの、止まる時。ダッシュボードとコマンドラインが共有する
  バージョン付きの `/api/v1` と、ブラウザのサインインは、2.7 の後の段で扱います
  ([後述](#what-is-not-here-yet))。
- **コード**: `cpersona/service.py` (中継の側)、`cpersona/entry.py` (コマンド)、
  `cpersona/server.py` の `local-service` トランスポート。

## なぜ { #why }

2.6 までは、`cpersona` を起動した MCP クライアントごとに専用のプロセスができ、
そのプロセスがデータベースを開いてそのクライアントに応えていました。
クライアントを 3 つ開けば、1 つの SQLite ファイルに 3 つのプロセスが書き込み、
プロセス全体の状態 (埋め込みのキャッシュ、較正、no-persist の一時停止) も 3 組できます。
その横で、ダッシュボードはファイルを直接読んでいました。
同じツールを、2 つの処理の経路 (stdio のプロセス内と HTTP のサーバー) が担っていました。

2.7 からは、その人のマシンで記録先ごとに 1 つのサーバーが動きます。
stdio の起動はそのサーバーへの中継になるので、同じ記録先のクライアントは
1 つのプロセスと 1 つの書き手を共有します。処理の経路は HTTP のトランスポートだけになります。

クライアントの設定は変わりません。以前 `cpersona` を起動していた行が、今は中継を起動します。

## stdio の起動がすること { #what-a-stdio-launch-does }

1. 記録先を決める。`CPERSONA_DB_PATH` の絶対パス (未設定なら、相対の既定値
   `data/cpersona.db` をクライアントの作業ディレクトリから解決したもの)。
2. その記録先のロックを取り、サービスの記録を読む。記録されたポートで
   この記録先のサービスが応えたら、設定を確かめて ([次の節](#which-service-a-client-uses)) それを使う。
3. 応えなければ、クライアントから切り離して 1 つ立ち上げ
   ([方法](#starting-a-service-that-outlives-its-client))、応えるまで待ってから記録する。
4. クライアントのメッセージを、ループバックの HTTP でサービスへ転送する。
   転送には既存の stdio のプロキシ (`cpersona/proxy_stdio.py`) を使い、
   サービスのトークンとこの接続の名前を付け足す。

中継はサーバーを import しません。重いものを読み込む前に、コマンドが引数と環境変数から
何を動かすかを決めます。そのため、中継にかかる時間はサーバー自身の起動のごく一部です。

## クライアントが使うサービス { #which-service-a-client-uses }

サービスは**記録先**と**このパッケージのバージョン**で区別します。
バージョンが違えば別のサービスになります。2 つのバージョンの stdio サーバーが
別のプロセスだったのと同じです。古い方は、決まった時間だけ使われずにいると止まります。

クライアントの**設定**もサービスに伝わります。`CPERSONA_*` と `EMBEDDING_*` の変数は、
1 つの接続を表す少数のものを除いて、すべて記録先の設定とみなします。除くものは
`CPERSONA_TRANSPORT`・`CPERSONA_REMOTE_URL`・`CPERSONA_AUTH_TOKEN`・
`CPERSONA_PROXY_MAX_INFLIGHT`・`CPERSONA_HTTP_HOST`・`CPERSONA_HTTP_PORT`・
`CPERSONA_LOCAL_SERVICE`・`CPERSONA_SERVICE_DIR` と、中継がサービスに渡す変数です。
パスの設定 (名前が `_PATH`・`_FILE`・`_DIR` で終わるもの) は、指している絶対パスで比べます。

動いているサービスと設定が違うクライアントは**拒否**します。そのクライアントが送る要求には、
すべてエラーで答えます。エラーは違う設定の名前を挙げ、値は含めません。
ほかの答え方も考えられましたが、どちらも悪くなります。

- 違う設定のサービスで応えると、クライアントが求めた設定が黙って失われる。
- 同じ記録先に 2 つ目のサービスを立てると、サービスが無くすはずの 2 つ目の書き手が戻る。

比較には設定ごとの鍵付きハッシュを使います。鍵はサービスの起動時に作る乱数です。
そのため、サービスが自分について答える内容には、どの設定の値も含まれません。
埋め込みの API キーのような秘密も同じです。

## サービスが受け付けるもの { #what-the-service-accepts }

サービスは、中継が設定する `local-service` という名前で HTTP のトランスポートを動かします。
HTTP のトランスポートを配備した場合とは、受け付けるものが違います。

- `127.0.0.1` にだけ bind する。
- すべての要求にサービスの**トークン**が要る。中継はサービスの記録からトークンを読む。
  記録は所有者だけが読める。トークンはサービスを立ち上げるたびに新しくなる。
- **Host** ヘッダーは、ループバックのアドレスとサービスのポートでなければならない。
  自分のドメイン名を `127.0.0.1` に向けたウェブページは、その名前を送るので拒否される。
- CORS も OAuth の情報の公開も、すべてを受ける経路も持たない。あるのは `/mcp/`・
  `/api/v1/instance`・`/api/v1/stop` だけで、ほかのパスは 404 になる。
- ACL のファイルがあれば、すべての要求を予約済みの `local` プリンシパルとして扱う。
  stdio のプロセスと同じ ([ACL の設計 §5.4](ACL_DESIGN.md))。
- その人のマシンでその人に応えるので、2 つのトランスポートで挙動が分かれる所では
  stdio のサーバーと同じに振る舞う。`open_dashboard` はこのマシンでページを開く。

`/api/v1/instance` は、サービスが何者かを答えます (パッケージのバージョン、鍵、記録先、
プロセス ID、設定のハッシュ、止まるまでの時間)。止まりかけている間は `503` を返すので、
中継が、閉じる直前のサービスにクライアントを渡すことはありません。
`/api/v1/stop` はサービスに停止を求めます。バージョン付きの API は、2.7.0a2 でこの 2 つから広げます。

## セッションの鍵を申告しない呼び出し元 { #callers-that-declare-no-session-key }

`session_key` を送らない呼び出し元は、これまで stdio のプロセスが持つ 1 つの箱に入りました。
その箱は、そのクライアント専用でした。複数のクライアントが共有するサービスでは、
この箱も共有になります。あるクライアントが鍵を付けずに `pause_persistence` を呼ぶと、
別のクライアントの書き込みまで黙って捨てられます。

そこで、中継はそれぞれ自分の接続に名前を付けます (起動ごとの乱数の ID を
`X-CPersona-Connection` ヘッダーで送る)。サービスはその名前を、鍵を申告しない呼び出し元の箱にします
([セッションの同一性](SESSION_IDENTITY_DESIGN.md))。この箱は「申告なし」のままなので、
応答は stdio の時と同じに読めます (`scope: "process"`)。埋め込みの不調を知らせる手順の全文は
接続ごとに 1 回届き、`identity_shared` の印は付きません。鍵を申告した場合は以前と同じです。
リモートの HTTP のトランスポートは、このヘッダーを無視します。

## 動いている期間 { #lifetime }

- **使われていない時の停止**: `CPERSONA_SERVICE_IDLE_MINUTES` (既定 30、`0` で止めない) の間、
  何にも使われなければ止まる。処理中の要求も、接続しているクライアントも「使われている」に数える。
  中継は 5 分ごとに、まだ接続していることをサービスに知らせる。そのため、開いたまま静かな
  クライアントがサービスを失うことはなく、そのクライアントが掛けた一時停止も失われない。
- **明示の停止**: `cpersona service stop [KEY]`。`cpersona service list` は、
  記録されたサービスをトークン抜きで表示する。
- **立ち上げ直し**: 中継が接続先に誰もいないと分かった時 (使われずに止まった、落ちた、
  止まるまでの時間の間マシンがスリープしていた)、サービスを探すか立ち上げるのを 1 回だけ試し、
  メッセージを送り直す。まだ何も送っていないので、二重に動くことはない。
  それも失敗すれば、クライアントにはサービスのログの場所を示すエラーが返る。
  中継が、プロセス内でクライアントに応える形に切り替えることはない。切り替えると、2 つ目の経路が戻る。
- **起動の失敗**: 応える前に終了したサービス、または 60 秒以内に応えないサービスは、
  ログの最後の数行を添えて報告する。

## 立ち上げたクライアントより長く残るサービスの起動 { #starting-a-service-that-outlives-its-client }

サービスは、立ち上げたクライアントが終わっても残らなければなりません。
1 つのエディタを閉じたことで、別のエディタの記憶が止まってはいけないからです。
そのために何が要るかを、設計を決める前にプラットフォームごとに測りました。

- **macOS と Linux**: サービスを新しいセッションで起動する。クライアントのプロセスグループを
  強制終了しても残り、stdio で起動した ssh の接続を閉じても残る。
- **Windows**: サービスを切り離し、独自のプロセスグループで、クライアントが属するジョブの外に、
  すぐ終了する中継ぎのプロセスを通して起動する。どれも欠かせない。切り離しただけのプロセスは、
  起動したセッションと一緒に終わった。ジョブから外すとセッションの終了では残ったが、
  クライアントがプロセスのツリーごと終了すると一緒に終わった。ツリーは親子のつながりを
  たどるので、中継ぎのプロセスでそのつながりを切る。Windows ではサーバーの初回の起動が遅い
  (import のため) が、その後の接続は遅くない。
- **サンドボックスの中のクライアント**: ツールを読み取り専用のサンドボックスで動かすクライアントからも、
  ループバックのサービスに届き、サービスはクライアントの終了後も残った。

## ファイル { #files }

`~/.cpersona/services/` (`CPERSONA_SERVICE_DIR` で移せる)。所有者だけが読める。

| ファイル | 中身 |
|---|---|
| `<key>.json` | ポート、プロセス ID、バージョン、起動時刻、記録先、トークン、ハッシュの鍵 |
| `<key>.lock` | 中継がサービスを探すか立ち上げる間、保持する |
| `<key>.log` | サービスの出力。起動時に 5 MB を超えていれば新しく始める |

key は、記録先のパスとバージョンのハッシュです。

## まだ無いもの { #what-is-not-here-yet }

- **2.7.0a2**: バージョン付きの `/api/v1` の契約と、データベースのファイルを読む代わりに
  その API のクライアントになるダッシュボード。
- **2.7.0a3**: 手元のサービスとリモートのサーバーに共通の、1 つのブラウザのサインイン。
- **2.7.0b1**: プロセス内の stdio サーバーと `CPERSONA_LOCAL_SERVICE` を消す。
  `open_dashboard` と、ダッシュボード専用のサーバーとサインインも消す。
- 2.7 では予定しないもの: サービスを OS のサービス管理に登録すること。
  サービスはクライアントが必要とした時に起動する。

## 不変条件 { #invariants }

1. 記録先とバージョンごとにサービスは 1 つ。同じ記録先・同じ設定の 2 つ目のクライアントは、
   動いているサービスに加わる (`tests/test_local_service.py` の、実際のサービスを立ち上げる試験)。
2. 設定が違うクライアントは拒否し、違う設定の名前だけを挙げて値は出さない。
3. トークンとループバックの Host が無い要求は、MCP の窓口に届かない。
4. 鍵を申告しない呼び出し元のプロセス内の状態は、その接続のもの。ある接続の一時停止が、
   別の接続の書き込みを捨てることはない。
5. サービスが止まるのは、使われていない時 (処理中の要求が無く、最近の要求も知らせも無い) か、
   停止を求められた時だけ。
6. 中継がメッセージを送り直すのは、何も送っていない時だけで、1 回だけ。
